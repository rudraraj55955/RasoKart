## 2. Login Flow

### Steps

1. Go to `https://rasokart.com/` and select **Merchant Portal**
2. Enter your registered email and password
3. Click **Sign In**

### Password Reset

- Click **Forgot Password** on the login page
- Enter your registered email
- Follow the reset link sent to your inbox

### OTP Login (When Enabled)

- Click **OTP** tab on the login page
- Enter your email and the OTP sent to your inbox
- OTPs expire in 10 minutes

### Account States After Login

| Status | What Happens |
|---|---|
| `approved` | Full portal access |
| `pending` | Redirected to pending screen; contact support |
| `rejected` | Redirected to rejected screen; reason shown |
| `suspended` | Redirected to suspended screen; contact support |

## 3. KYC Flow

KYC (Know Your Customer) is mandatory before payment collection is enabled.

### Step-by-Step

#### A. Manual Document Submission (Merchant → Verification)

1. Navigate to **Merchant → Verification**
2. Upload required documents:
   - PAN Card (mandatory)
   - Aadhaar Card (mandatory)
   - Bank proof / cancelled cheque (mandatory)
   - GSTIN certificate (optional)
   - CIN / Company registration (optional)
3. Submit for review
4. Status updates: `submitted → pending → approved / rejected`

#### B. Automated KYC via DigiLocker (Merchant → Secure Onboarding)

1. Navigate to **Merchant → Secure Onboarding**
2. Verify your mobile number via OTP
3. Provide consent for data access
4. Verify PAN (automated via Secure ID)
5. Verify Aadhaar via DigiLocker
6. Add bank account details
7. Optionally add GSTIN / CIN / Udyam
8. Submit for final review

### KYC Status Reference

| Status | Meaning |
|---|---|
| `submitted` | Documents received, pending review |
| `pending` | Under review by admin |
| `approved` | All documents verified; payment collection enabled |
| `rejected` | One or more documents rejected; reason shown in Profile |
| `re_upload_required` | Re-submission required for specific document(s) |

### Rejection Handling

- Rejection reason is shown in **Merchant → Profile** (account status banner)
- Re-submit the rejected document(s) via **Merchant → Verification**
- Admin reviews the re-submission

## 4. Plan & Service Activation

### How Plans Work

Plans are assigned by a Super Admin. Merchants cannot self-assign plans.

After plan assignment:
- Transaction limits take effect immediately
- API / webhook access flags are applied
- Settlement and deposit fees are configured per plan

### Viewing Your Plan

Go to **Merchant → My Plan** to see:
- Plan name and tier
- Expiry date (if applicable)
- Settlement fee % and deposit fee %
- All usage limits with current consumption
- API access and webhook access flags
- Plan history and invoices

### Service Activation

Additional services (beyond the default payment collection) are activated by request:

1. Go to **Merchant → RasoKart Services**
2. Click **Request Early Access** on the desired service
3. Optionally add a note describing your use case
4. Admin reviews and activates the service
5. You receive an email notification on approval

### Service Status Labels

| Label | Meaning |
|---|---|
| 🟢 **Live** | Service is active on your account |
| 🔵 **Not Available** | Service not yet available; request access |
| 🟡 **Pending Approval** | Activation request submitted, under review |
| 🟢 **Approved** | Admin approved; activation in progress |
| 🔴 **Not Available** | Previous request was rejected; reapply |

## 6. API Integration

> **Requires:** Silver, Gold, Platinum, or Custom plan

### Base URL

```
https://rasokart.com/api
```

### Authentication

Every API request must include both credentials in headers:

```http
X-Api-Key: rasokart_live_<your-api-key>
X-Api-Secret: rasokart_secret_<your-secret-key>
```

> ⚠️ **Never** include `X-Api-Key` or `X-Api-Secret` in client-side JavaScript, mobile app bundles, or public source code repositories.

### Available Merchant Endpoints

| Method | Path | Description |
|---|---|---|
| `GET` | `/merchant/transactions` | List transactions with filters |
| `GET` | `/merchant/transactions/:id` | Get a single transaction |
| `POST` | `/merchant/payin/orders` | Create a new payment order |
| `GET` | `/merchant/payin/orders/:id` | Check payment order status |
| `GET` | `/merchant/qr-codes` | List QR codes |
| `POST` | `/merchant/qr-codes` | Create a dynamic QR code |
| `GET` | `/merchant/virtual-accounts` | List virtual accounts |
| `POST` | `/merchant/virtual-accounts` | Create a virtual account |
| `GET` | `/merchant/payment-links` | List payment links |
| `POST` | `/merchant/payment-links` | Create a payment link |
| `GET` | `/merchant/settlements` | List settlements |
| `GET` | `/merchant/ledger` | View wallet ledger |
| `GET` | `/merchant/balance` | Current wallet balance |

For full documentation with request/response schemas and Try It panels, see **Merchant → API Docs**.

### Example: Create a Payment Order

```bash
curl -X POST https://rasokart.com/api/merchant/payin/orders \
  -H "X-Api-Key: rasokart_live_..." \
  -H "X-Api-Secret: rasokart_secret_..." \
  -H "Content-Type: application/json" \
  -d '{
    "amount": 100.00,
    "currency": "INR",
    "merchantReference": "ORDER-12345",
    "customerEmail": "customer@example.com",
    "customerPhone": "9876543210",
    "description": "Product purchase"
  }'
```

### Example Response

```json
{
  "orderId": "RK_ORD_abc123",
  "checkoutUrl": "https://rasokart.com/checkout/abc123",
  "status": "INITIATED",
  "amount": 100.00,
  "currency": "INR",
  "merchantReference": "ORDER-12345",
  "expiresAt": "2026-08-13T21:00:00Z"
}
```

Redirect your customer to `checkoutUrl` to complete payment.

### Payment Status Values

| Status | Meaning |
|---|---|
| `INITIATED` | Order created; awaiting customer payment |
| `PENDING` | Payment in progress; not yet confirmed |
| `SUCCESS` | Payment completed and wallet credited |
| `FAILED` | Payment failed; no funds collected |
| `REVERSED` | Payment reversed by provider |
| `REFUNDED` | Payment refunded to customer |
| `EXPIRED` | Order expired before payment was made |

## 7. API Credentials

### Generating an API Key

1. Go to **Merchant → API Keys**
2. Click **Generate Key**
3. Optionally enter a label (e.g. "Production App")
4. Click **Generate**
5. Copy both the **API Key** and **Secret Key** immediately

### Key Format

| Field | Format Example |
|---|---|
| API Key | `rasokart_live_<48 hex chars>` |
| Secret Key | `rasokart_secret_<64 hex chars>` |

### Security Rules for API Credentials

- Store keys in environment variables, not in source code
- Use separate keys per environment (staging / production)
- Rotate keys immediately if compromised
- Revoke unused keys
- Monitor "Last Used" timestamps for unexpected activity

### Key Management

| Revoke a key | Merchant → API Keys → trash icon on the key row |

## 8. Webhook / Callback Setup

### Terminology

| Term | Direction | Purpose |
|---|---|---|
| **Outbound Webhook** | RasoKart → Your server | RasoKart notifies you of payment events |
| **Inbound Callback** | Your server → RasoKart | You notify RasoKart of payment results (e.g. after UTR confirmation) |

### Setting Up Outbound Webhooks

1. Go to **Merchant → Webhook Settings**
2. Enter your **Callback URL** (must be publicly reachable HTTPS)
3. Select **Event Types** to subscribe to:
   - `payment.success` — Payment completed
   - `payment.failed` — Payment failed
   - `payment.pending` — Payment pending confirmation
   - `va.credited` — Virtual account received credit
4. Configure **retry policy** (max retries, retry delays)
5. Click **Save**

### Webhook Event Payload

```json
{
  "event": "payment.success",
  "timestamp": "2026-08-13T20:00:00Z",
  "data": {
    "orderId": "RK_ORD_abc123",
    "merchantReference": "ORDER-12345",
    "transactionId": 456,
    "amount": 100.00,
    "currency": "INR",
    "merchantId": 42,
    "status": "SUCCESS",
    "utr": "UTR987654321",
    "paymentMethod": "upi"
  }
}
```

### Webhook Delivery

- RasoKart will `POST` the event payload to your configured URL
- Your server must respond with HTTP `200` within 30 seconds
- Non-`200` responses trigger automatic retries per your retry policy
- Retry delays are configurable (default: 1 min, 5 min, 30 min)

### Testing Webhooks

1. Go to **Merchant → Webhook Settings**
2. Scroll to the **Test** section
3. Select an event type
4. Click **Send Test Event**
5. View the delivery result (HTTP status, response body, duration)

### Viewing Webhook Logs

**Merchant → Webhook Settings → Delivery Logs** shows:
- Event type
- Delivery timestamp
- HTTP status code from your server
- Response body (truncated)
- Attempt count
- Next retry time (if pending)
- Manual retry button

**Merchant → Callbacks** shows the inbound callback log:
- Status (delivered / failed / pending retry)
- Signature verification result
- Event type
- HTTP status from RasoKart's side
- Attempt history per callback

### Callback URL Requirements

- Must be HTTPS (port 443)
- Must be publicly reachable (no localhost, no VPN-only URLs)
- Must respond within 30 seconds
- Must return HTTP `200` on success
- Must NOT be a redirect URL — follow redirects on your side

## 9. Signature Verification

### Outbound Webhook Secret (RasoKart → Your Server)

RasoKart signs every outbound webhook with an `X-Signature` header.

**Header format:**
```
X-Signature: sha256=<hex-encoded HMAC-SHA256>
```

**How to verify (Node.js):**

```javascript
const crypto = require("crypto");

const WEBHOOK_SECRET = process.env.RASOKART_WEBHOOK_SECRET;

function verifyRasoKartWebhook(rawBody, signatureHeader) {
  // signatureHeader = req.headers['x-signature']
  const expected = "sha256=" + crypto
    .createHmac("sha256", WEBHOOK_SECRET)
    .update(rawBody)   // rawBody must be the raw bytes, not parsed JSON
    .digest("hex");
  return crypto.timingSafeEqual(
    Buffer.from(signatureHeader),
    Buffer.from(expected)
  );
}
```

**How to verify (Python):**

```python
import hmac
import hashlib
import os

WEBHOOK_SECRET = os.environ["RASOKART_WEBHOOK_SECRET"]

def verify_rasokart_webhook(raw_body: bytes, signature_header: str) -> bool:
    expected = "sha256=" + hmac.new(
        WEBHOOK_SECRET.encode(),
        raw_body,
        hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(signature_header, expected)
```

**Important:** Always use `timingSafeEqual` / `compare_digest` — never use `==` to compare signatures (timing attack risk).

### Inbound Callback Secret (Your Server → RasoKart)

When your server sends callbacks to RasoKart, sign the request body with your **callback signing secret**.

**Generate a callback signing secret:**
1. Go to **Merchant → Webhook Settings → Callback Signing Secret**
2. Click **Generate Secret**
3. Copy the secret immediately — it is shown **only once**

**Signing your callback (Node.js):**

```javascript
const crypto = require("crypto");

const CALLBACK_SECRET = process.env.RASOKART_CALLBACK_SECRET;

function signCallbackBody(rawBody) {
  return "sha256=" + crypto
    .createHmac("sha256", CALLBACK_SECRET)
    .update(rawBody)
    .digest("hex");
}

// Add to your outgoing request headers:
// X-Signature: sha256=<hex>
// X-Timestamp: <unix epoch seconds>
// X-Nonce: <unique UUID per request> (recommended for replay protection)
```

### Replay Protection

RasoKart validates the `X-Timestamp` header on inbound callbacks:
- Must be within **±5 minutes** of server time
- Optional `X-Nonce` header prevents exact duplicate replays
- Ensure your server clock is synchronized (NTP)

### Secret Rotation

Rotate your secrets every 90 days (dashboard shows a warning at 80 days):

1. Go to **Merchant → Webhook Settings → Callback Signing Secret**
2. Click **Rotate Secret**
3. Confirm the rotation
4. Copy the new secret immediately
5. Update your servers with the new secret before the old one expires

> ⚠️ The old secret stops working immediately on rotation. Update your servers first.

## 10. Security Rules

### Credentials

| Rule | Detail |
|---|---|
| API Secret Key shown once | Copy immediately; lost key must be revoked and regenerated |
| Callback signing secret shown once | Same as API secret — copy and store securely |
| Keys stored as environment variables | Never in source code, `.env` committed to VCS, or client-side bundles |
| Separate keys per environment | Use different keys for staging and production |
| Immediate revocation on compromise | Revoke via API Keys page; generate a new key |
| Rotate callback secret ≤ 90 days | Dashboard reminds you at 80 days |

### Request Verification

| Rule | Detail |
|---|---|
| Always verify X-Signature | Never trust a webhook without verifying HMAC-SHA256 |
| Use timing-safe comparison | `timingSafeEqual` / `compare_digest` only — never `==` |
| Validate X-Timestamp | Reject requests older than 5 minutes |
| Use X-Nonce | Include a UUID nonce to prevent replay attacks |
| Verify raw body | Parse JSON after verifying the signature, not before |

### Isolation Rules

| Rule | Detail |
|---|---|
| Account isolation enforced at API level | Your API key can only access your own account's data |
| Cross-merchant access rejected with 403 | No query parameter can override merchantId scoping |
| Admin endpoints unreachable | Admin-only routes return 403/404 for merchant API keys |
| Provider credentials never exposed | PayU/Razorpay/Cashfree credentials are not returned in any merchant API response |

### Rate Limiting

| Endpoint | Limit |
|---|---|
| Login | 5 attempts per 15 minutes per IP |
| API key generation | 10 per hour per merchant |
| Webhook test | 20 per hour per merchant |
| API requests (general) | Depends on plan; contact support for limits |

- Access another merchant's data (any attempt returns 403)

- Approve or modify their own KYC status
- Assign or change their own plan
- Activate their own payout service without admin approval
- Modify transaction status or wallet balance
- Access Super Admin IAM/RBAC settings
- Access admin-only reports or reconciliation data
- Bypass transaction or QR code limits

## 13. Go-Live Checklist

Work through this checklist in order. Each step requires the previous one to be complete.

```
□ STEP 1 — Account Created
  → Super Admin creates merchant account
  → Merchant receives login credentials
  → Merchant can log in successfully

□ STEP 2 — Contact Verified
  → Merchant email is on file and working
  → Merchant can receive notification emails
  → Login alert email is delivered successfully

□ STEP 3 — KYC Submitted
  → Merchant completes business profile (Merchant → Profile)
  → All required documents submitted (PAN, Aadhaar, bank proof)
  → Submission status: "Submitted" or "Under Review"

□ STEP 4 — KYC Approved
  → Super Admin reviews and approves all documents
  → Merchant status updated to "approved"
  → Merchant receives KYC approval notification

□ STEP 5 — Plan Assigned
  → Super Admin assigns appropriate plan (Silver or higher for API)
  → Merchant can see plan name, limits, and fees in My Plan
  → No expiry warning shown

□ STEP 6 — Required Services Enabled
  → Super Admin enables payin service for merchant
  → At least one payment provider is active on merchant's account
  → Dashboard shows "Provider Status: 1 Active"

□ STEP 7 — API Setup (Required for API Integration Only)
  → Plan includes API access (Silver+)
  → Merchant generates API key via Merchant → API Keys
  → Merchant copies and securely stores API Key + Secret Key
  → Test API call returns 200 (not 401/403)

□ STEP 8 — Callback Verified (Required for API Integration Only)
  → Merchant sets Callback URL in Merchant → Webhook Settings
  → Merchant generates callback signing secret
  → Merchant adds signature verification to their server
  → Test webhook delivery returns HTTP 200 from merchant's server
  → Webhook log shows "Success" status

□ STEP 9 — LIVE Approved
  → Super Admin confirms merchant is live-ready
  → Provider is in LIVE mode (not UAT/test)
  → A small live verification payment (if required) passes
  → Admin confirms approval in Admin → Merchants

□ STEP 10 — Merchant Ready
  → Dashboard shows "Onboarding Progress" all required steps complete
  → Merchant can collect live payments via QR code / API / payment link
  → Merchant receives payment notifications
  → Wallet balance is updated on successful payment
```

## Appendix: Do Not Expose

The following are RasoKart **internal infrastructure credentials** and must **never** be shared with merchants or exposed in merchant-facing APIs:

- PayU `Key` and `Salt`
- Razorpay `key_id`, `key_secret`, and `webhook_secret`
- Cashfree `clientId` and `clientSecret`
- EKQR `apiKey` and `apiSecret`
- Any database connection string
- Any `SESSION_SECRET` or encryption key value

Merchants receive **only**:
- Their own RasoKart API Key + Secret Key
- Their own callback signing secret
